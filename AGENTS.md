# Инструкции Codex для PracticeFlow

Эти правила действуют для всего репозитория. Следуй также
[CONTRIBUTING.md](CONTRIBUTING.md) и инструкциям в подкаталогах.

## Обязательное завершение задач через GitHub

Владелец разрешил Codex после завершения каждой задачи с изменениями кода,
тестов, настроек или документации самостоятельно создавать коммиты, отправлять
ветку, открывать pull request и сливать его в `main`. Повторное подтверждение
для этих действий не требуется. Явное указание пользователя в текущей задаче
оставить изменения локально, не публиковать или не сливать имеет приоритет.
Для консультаций и задач без изменений пустые коммиты и PR не создавай.

- Единственный целевой репозиторий:
  [bekw-eg/PracticeFlow](https://github.com/bekw-eg/PracticeFlow).
- Базовая и итоговая ветка: `main`.
- Рабочие ветки создавай с префиксом `codex/`.
- Отправляй изменения через pull request. Прямой push в `main` запрещён.
- Задача с изменениями считается завершённой после подтверждённого merge PR
  в `main`, если пользователь не ограничил публикацию и нет внешнего блокера.

## Только от имени владельца

Все GitHub-действия выполняй только под учётной записью `bekw-eg`.

Перед первым push, созданием PR и merge проверь активную учётную запись через
`gh api user --jq .login` и целевой репозиторий через `git remote -v`.
Проверь также окружение аутентификации фактически используемых инструментов:
Git push должен пользоваться credentials этой же учётной записи, а не другого
пользователя, бота, GitHub App или отдельного сервисного аккаунта.

Для коммитов в рабочем checkout используй локальную Git-конфигурацию:

```powershell
git config --local user.name "bekw-eg"
git config --local user.email "217148214+bekw-eg@users.noreply.github.com"
```

Author и Committer должны соответствовать этой конфигурации. Проверь их перед
push через `git log -1 --format=fuller`. При переопределениях GIT_AUTHOR_* или
GIT_COMMITTER_* обеспечь правильную личность для создаваемого коммита, не выводя
секреты окружения. Не меняй глобальные настройки Git.

Не добавляй подписи, авторов или `Co-authored-by` для Codex, OpenAI, AI-ботов
и других лиц. Не используй чужие credentials и не подделывай подтверждение
авторства. Если авторизация `bekw-eg` недоступна или личность нельзя проверить,
сохрани работу локально и сообщи конкретный блокер. Не переключайся на другой
аккаунт ради завершения задачи.

## Порядок работы

1. Изучи текущее состояние Git, уже открытые PR и инструкции репозитория.
   Сохрани существующие пользовательские изменения. Не включай чужие или
   не относящиеся к задаче файлы в свой коммит.
2. Получи актуальный `origin/main`. Для новой задачи используй отдельную ветку
   от него. При грязном рабочем дереве предпочитай отдельный checkout/worktree;
   не сбрасывай изменения и не прячь их в stash без необходимости.
   Если продолжаешь ранее начатую задачу, используй её подходящую ветку и PR.
3. Реализуй задачу и выполни релевантные проверки из CONTRIBUTING.md.
   Перед коммитом просмотри diff и добавь только конкретные файлы задачи.
   Не используй без проверки `git add .` или `git add -A`.
4. Не коммить `.env`, секреты, реальные студенческие документы, данные tenant,
   приватные выгрузки, локальные журналы и временные артефакты. Проверь состав
   коммита и Git-личность, затем отправь рабочую ветку в целевой репозиторий.
5. Создай PR в `main` от `bekw-eg` или обнови существующий PR этой задачи.
   Заполни шаблон .github/PULL_REQUEST_TEMPLATE.md: итоговое поведение,
   выполненные проверки и реальные ограничения. Не заявляй проверки,
   которые не выполнялись. После создания PR прикрепи его к текущему чату
   через attach_artifact, если этот инструмент доступен.
6. Проверь diff PR, его автора, целевой репозиторий, базовую ветку и head SHA.
   Дождись завершения проверок CI. Исправь относящиеся к задаче ошибки и
   повтори проверки после новых коммитов. Не сливай PR с проваленными или
   незавершёнными релевантными проверками и обязательными status checks.
7. После успешных проверок выполни merge через GitHub от `bekw-eg`.
   Предпочитай обычный merge commit, сохраняющий авторство исходных коммитов.
   Используй проверенный head SHA при merge, чтобы не слить неожиданно
   изменившуюся ветку. Соблюдай branch protection и обязательные approvals;
   не применяй `--admin`, не отключай проверки и не обходи ограничения.
8. Подтверди через GitHub, что PR имеет состояние MERGED и был слит в `main`
   пользователем `bekw-eg`. Обнови локальные remote refs. Обновляй локальную
   `main` только если это безопасно для текущего checkout и пользовательских
   изменений; иначе оставь рабочее дерево как есть и сообщи об этом.
9. В финальном ответе дай ссылку на PR, краткий результат проверок и состояние
   merge. Не останавливайся после локальной реализации, если push, PR и merge
   разрешены и доступны.

Если merge блокируют права, обязательное одобрение, конфликт, сбой GitHub или
проверки, которые нельзя исправить в рамках задачи, сохрани доступный результат
в ветке/PR и укажи точный блокер. Не сообщай об успешном merge без подтверждения.
Не используй force push в `main`, destructive reset или переписывание чужой
истории ради выполнения этих правил.
