# Правила документа и повторные проверки

Реализация от 15 сентября 2026 года. Тесты, сборка и миграция в этой сессии
не запускались по просьбе пользователя. Выполнен разбор синтаксиса изменённых
Python/TypeScript-файлов без исполнения приложения. Это не подтверждает работу
API, PostgreSQL-триггеров или интерфейса в браузере.

## Интерфейс

Экран `/document-checks/:submissionId` сохраняет HTML-документ справа и добавляет
слева вкладки «Замечания» и «Правила».

- В «Правилах» доступны все существующие параметры профиля, добавление,
  отключение и удаление правил. У основного текста и заголовков отдельные поля.
- Для глав, подразделов и пунктов можно задать шрифты, диапазон размера,
  жирность, выравнивание, интервалы и отступы. Новые требования заголовков
  по умолчанию используют CENTER; глава — 16 пт, подраздел и пункт — 14 пт.
  Настройки существующих уровней выбранного профиля сохраняются.
- Выбор абзаца в документе при открытой вкладке «Правила» показывает его
  автоматически распознанный тип. Можно выбрать другой тип или вернуть
  автоматическое распознавание. Фрагменты одного исходного абзаца на разных
  HTML-страницах выбираются вместе.
- «Сохранить» сохраняет настройки без запуска анализа. «Перепроверить» сначала
  сохраняет изменения, затем ставит новый запуск в очередь. Ввод значений сам
  по себе не запускает worker.
- Показаны версия сохранённых настроек и версия настроек показанного результата.
  Несохранённые изменения и ошибки сохранения видны; неудачный запрос или
  фоновое обновление не сбрасывает форму. При конфликте двух вкладок можно явно
  загрузить сохранённое либо сохранить свою форму поверх последней версии.
- В «Замечаниях» есть история готовых результатов и раскрываемые правила,
  использованные именно в выбранном запуске, включая ручные типы абзацев.
- Во время нового запуска или после его ошибки предыдущий готовый результат
  доступен. Новые замечания и счётчики показываются вместе после получения
  полного списка; прежняя подсветка до этого сохраняется.

Добавлены русский, казахский и английский тексты интерфейса, параметров и
ошибок оформления. Выравнивание показывается словами, например «По центру» и
«По левому краю».

## Хранение и запуск

- `teacher_document_submissions` и приватные DOCX остаются неизменяемыми.
- `document_check_settings` хранит правила, `paragraph_overrides` и `revision`
  по паре `(organization_id, submission_id)`. Имя файла не является ключом.
- При новой загрузке настройки копируются из закреплённой версии профиля.
  Если заголовков нет, добавляются требования уровней 1–3; если часть уровней
  отсутствует, добавляются недостающие. Это касается только настроек документа.
  Старые документы получают настройки при первом открытии панели; их прежние
  задания и опубликованные правила не переписываются.
- Запуски имеют возрастающий `run_number`, необязательный `idempotency_key` и
  неизменяемый JSON-снимок `settings_snapshot`. Создание запуска и его правил —
  одна транзакция. Блокировка строки настроек согласует сохранение, снимок и
  выделение очередного номера.
- `document_check_run_rules` содержит реальные неизменяемые идентификаторы
  правил запуска. Новые замечания используют `run_rule_id`, исторические —
  прежний `check_rule_id`. Ограничения требуют ровно один из этих идентификаторов;
  составной FK привязывает новое замечание к правилу того же tenant и запуска.
- ORM запрещает изменение завершённых заданий и правил запуска. PostgreSQL
  дополнительно защищает снимок задания, соответствие правил снимку и
  принадлежность замечаний активным правилам выполняющегося задания.
- Worker использует правила запуска и ручную классификацию из снимка.
  Сохранение настроек во время анализа не влияет на уже запущенную работу.
- Повторная отправка одного ключа возвращает тот же запуск, в том числе после
  его завершения. Тот же ключ с другой версией настроек даёт `409`. Разные ключи
  создают отдельные упорядоченные запуски. Интерфейс блокирует повторное нажатие
  во время запроса и проверку той же версии, пока текущий запуск активен.
- Последний результат определяется максимальным `run_number` среди COMPLETED,
  а не временем завершения. Позднее завершение старого запуска не заменяет
  результат нового. Запросы замечаний и кэш привязаны к `job_id`.
- Существующие lease, ограничение времени, повторные попытки worker и контроль
  SHA-256 приватного оригинала сохранены.

## API

Префикс всех маршрутов: `/api/v1/document-checks/teacher/submissions/{id}`.
Требуются текущая организация, роль TEACHER и точный владелец документа.

| Метод | Суффикс | Назначение |
| --- | --- | --- |
| GET | `/settings` | Настройки документа и их версия |
| PUT | `/settings` | Сохранение `revision`, `rules`, `paragraph_overrides` |
| GET | `/paragraphs` | Типы и индексы исходных абзацев; без текста документа |
| POST | `/recheck` | `{ "revision": N }` и заголовок `Idempotency-Key` |
| GET | `/runs` | История запусков с обычной пагинацией |
| GET | `/runs/{job_id}` | Снимок правил и ручных типов конкретного запуска |
| GET | `/findings?job_id=...` | Замечания конкретного запуска |

Ответ документа содержит `job` (последний созданный запуск) и
`latest_completed_job` (последний готовый результат). `/paragraphs` принимает
`job_id` для ручных типов из снимка этого запуска. Параграфы автоматически
распознаются текущим кодом; ранее сохранённые замечания не пересчитываются.

## Распознавание и ограничения

Сначала используются уровень структуры и цепочка наследования стилей Word.
При отсутствии явной структуры используются стандартные названия разделов
на трёх языках, нумерация и несколько признаков оформления короткого абзаца.
Требуемые пользователем значения оформления не участвуют в распознавании.
Ручная классификация имеет приоритет. Отдельно отсекаются подписи рисунков и
таблиц, стили оглавления и подписи; эвристики не применяются к ячейкам таблиц.

Отдельные требования заголовков исполняются для настроенных уровней; обычные
правила шрифта и абзацев к этим уровням не применяются. Если активного правила
для уровня нет, действует прежняя общая проверка оформления. В конфигурациях
старых уровней отсутствующие дополнительные параметры означают «не проверять».

Распознавание эвристическое: нестандартные названия и оформление, сложные
многоуровневые списки и неоднозначные короткие абзацы могут требовать ручного
выбора. Автоматическая нумерация Word учитывается консервативно по свойствам
списка, но полноценного вычисления последовательностей `numbering.xml` нет.
Уровни 4–6 поддерживаются для совместимости, а новые требования создаются для
уровней 1–3. Нумерация стандартных разделов вроде «Введение» необязательна даже
при включённом требовании номеров.

Пропуск титульного листа сохранён. Если границу первой страницы определить
нельзя, результат сообщает `BOUNDARY_UNKNOWN`, а не отсутствие ошибок.
HTML-пагинация приблизительна, изображения остаются заглушками. Сложные
возможности Word, включая полный механизм вёрстки и все параметры таблиц и
нумерации, не воспроизводятся. CSS показывает прочитанное оформление и не
подгоняется под требования правил.

Исполняются PAGE_FORMAT_MARGINS, FONTS_SIZES, PARAGRAPH_SPACING_INDENTS и
HEADINGS. TABLES, FIGURE_CAPTIONS, REFERENCES, REQUIRED_SECTIONS и
SPELLING_LANGUAGES сохраняются и явно отмечаются как пока не исполняемые.

## Применение в текущем Docker Compose

Новых зависимостей нет. Для существующего development-стека с образами и
монтируемыми каталогами, из PowerShell:

```powershell
Set-Location 'C:\Users\zdeat\Downloads\practiceflow-phase3-backend-checkpoint_1'
docker compose stop backend document-check-worker frontend
docker compose up -d postgres redis
docker compose run --rm --no-deps --entrypoint alembic backend upgrade head
docker compose up -d backend document-check-worker frontend
```

Запускайте последнюю команду после успешной миграции. Новая ревизия Alembic —
`1d5e6f7a8b9c`, её родитель — `0c4d5e6f7a8b`. Таблицы и оригиналы не удаляются.
Миграция не переписывает исторические результаты. Downgrade намеренно
отказывается удалять уже сохранённые настройки или историю повторных запусков.
Для таких данных требуется исправление следующей миграцией, а не их потеря.
